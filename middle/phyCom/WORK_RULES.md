# 피지컬 컴퓨팅 수업자료 개발 규칙

이 문서는 프로젝트에 지속 적용되는 작업 규칙이다. 새 Work는 코드 수정 전에 이 문서와 `WORK_STATUS.md`를 읽고 현재 저장소 및 실제 코드와 대조한다.

## 1. 범위와 보안

- 작업 저장소는 `wisecst/class`, 작업 범위는 `middle/phyCom/`이다.
- `wisecst/physical-tools/circuit-editor/`는 읽기·참고 전용이며 수정하지 않는다.
- 지정 범위 밖 저장소나 경로에 접근해야 한다면 사용자에게 먼저 허가를 요청한다.
- 공개 저장소 문서에는 공개 가능한 개발 원칙과 기술 상태만 기록한다. 미공개 수업모형·연구·수업자료 아이디어, 개인정보, 학생정보, 계정·비밀번호·보안정보 등은 기록하거나 외부에 공유하지 않는다.

## 2. Work 간 상태 복구

- 현재 개발 Work 이름은 `Work피컴 개발중`으로 한다. 백업 Work는 `Work피컴YYMMDD` 형식으로 이름을 붙인다.
- 인수인계는 긴 대화나 과거 설명에 기대지 않는다. GitHub, `WORK_RULES.md`, `WORK_STATUS.md`를 기준으로 복구한다.
- 새 Work는 코드 수정 전에 다음 순서로 확인한다.
  1. `WORK_RULES.md` 읽기
  2. `WORK_STATUS.md` 읽기
  3. 현재 Git 브랜치·HEAD·status 확인
  4. 허용 범위의 실제 코드와 구조 확인
  5. 문서와 실제 Git·코드 상태 대조
- `WORK_STATUS.md`와 실제 Git·코드 사이에서 단순한 사실관계 또는 상태 기록 불일치를 발견하면, 허용 범위 안의 관련 자료와 코드를 끝까지 대조한 뒤 실제 상태에 맞게 문서를 스스로 정정한다. 단순 불일치를 하나 발견할 때마다 중단하거나 사용자에게 반복 확인을 요청하지 않는다.
- 가능한 범위의 상태 대조는 한 번에 끝까지 수행하고, 현재 구현 사실과 그 설계의 적절성 판단을 분리해 기록한다. 구현 사실만으로 설계가 검증되었다고 간주하지 않는다.
- 실제 코드 변경, 사용자 설계 판단, 수업 내용의 기술적 정확성·오개념 판단, 근거자료 간 충돌, 허용 범위 또는 보안 문제가 필요한 경우에는 변경 전에 관련 사실과 판단 지점을 모아 사용자에게 보고하고 지시를 기다린다. 단순 상태 동기화와 명백한 기록 수정은 반복 승인을 요구하지 않는다.
- 특정 Mac, 로컬 폴더, 로컬 프로그램에 의존하지 않도록 한다. 사용자가 iPhone, iPad, Mac, Windows에서 Work를 이어갈 수 있어야 한다. Cloud Work와 GitHub를 주 개발 기반으로 하며 로컬 도구는 보조 수단이다.

## 3. 기초자료와 내용 근거

- 수업자료의 내용이나 구조를 개발·수정하기 전에 사용자가 제공하거나 지정한 자료가 있는지 확인한다. 교과서, 교육과정, 성취기준, 제공 PDF·PPT·문서, 프로젝트 내부 기존 자료, 허용된 참고 저장소, 사용 모듈의 공식 사양 및 신뢰할 수 있는 기술자료를 우선 검토한다.
- AI의 기억이나 추측만으로 제공 자료를 대체하지 않는다.
- 자료 간 충돌이나 확정 설계와 근거 자료 사이에 판단이 필요한 차이가 있으면 근거와 차이를 사용자에게 보고한다. 참고자료는 정확성 확인에 사용하며 그대로 복사하는 것이 목적은 아니다.

## 4. 코드 수정 전 분석과 최소 변경

- 관련 HTML/DOM, CSS, JavaScript, 함수, 이벤트 리스너, 상태·단계·애니메이션 로직, 공통 코드, 기존 임시 보정과 이전 수정 내역을 먼저 조사한다.
- 새 코드를 추가하기 전에 기존 구현으로 해결 가능한지, 실제 원인이 무엇인지 판단한다.
- 요청과 직접 관계없는 정상 기능과 디자인은 유지하고, 문제 해결에 필요한 최소 범위만 수정한다.
- 공통 CSS/JS 변경은 다른 페이지와 향후 모듈에 미치는 영향도 살핀다.
- 같은 기능을 새로 중복 구현하지 않는다. 기존 기능을 뒤쪽 CSS override로 덮어써 문제를 누적 해결하지 않는다.

## 5. 최적화, 모듈화, 확장성

모든 코드 수정에서 다음을 기본 점검한다: 중복 DOM·CSS·override·JavaScript·이벤트·상태, 미사용 코드, 임시 패치, 불필요한 예외 처리, 같은 기능의 다중 구현, 공통화 가능성. 중복·임시 보정이 확인되면 기존 구현을 분석해 기준 구현을 정하고 불필요한 코드를 정리한 뒤 최소 변경한다. 기능이 동작한다는 이유만으로 최적화 검토를 생략하지 않는다.

파일 분리와 공통화는 유지보수성, 재사용성, 기능 책임, 확장성, 현재 구조의 복잡도를 따져 결정한다. 파일 수만 늘리는 분리나 성급한 공통화는 하지 않는다. 큰 구조 변경·파일 분리 전에 이유, 변경 파일, 공통/전용 기능, 영향 범위, 장점과 주의점을 사용자에게 보고하고 확인을 받은 뒤 진행한다.

LED 외에도 수동버저, 서보모터, DC모터 및 기타 입출력 모듈에 적용될 가능성을 검토한다. 기본 레이아웃, 전환·전체화면·프리젠터·방향키/버튼, 강조와 순서 안내, 애니메이션, 회로 표현, 엔트리 UI, 실행 결과, 공통 디자인은 재사용 가치가 확인될 때 `common` 영역으로 분리할 수 있다.

## 6. 개발판과 공유판

- 웹 기반 개발판은 인터랙션, 애니메이션, 회로 연결 과정, 엔트리 단계별 동작 및 실행 결과를 포함하는 개발·수업용 원본으로 관리한다.
- 모듈의 개발과 안정성 검토 후 외부 공유판은 Google Slides를 우선 고려한다. 공유판은 교사가 쉽게 복제·사용할 수 있고, 개발용 전체 HTML/CSS/JS 소스 및 외부 파일 의존성을 최소화하며 필요한 경우 수정 가능한 형태를 지향한다.
- 두 판의 역할을 구분하고, 개발판 구현을 외부 공유를 위해 반드시 전체 소스로 제공해야 하는 구조에 불필요하게 종속시키지 않는다.

## 7. 애니메이션과 GIF

- 단계별 블록 이동, 번호, 강조, 설명 및 회로 연결은 우선 슬라이드 전환·단계 분리·도형·기본 애니메이션으로 표현한다. 실제 연속 움직임이 학습 이해에 필요한 경우에만 영상/GIF를 검토한다.
- GIF는 전체 화면이 아니라 필요한 최소 영역과 시간만 포함하고 용량을 줄인다. LED의 전구 깜빡임과 PWM 자동실행은 후보일 뿐, 확정된 제작 항목이 아니다.
- 최종 배포 GIF를 생성·확정하기 전 대상 페이지, 움직임, 범위, 반복 여부, 속도/시간, 용도, 슬라이드 기능으로 대체할 수 없는 이유를 사용자에게 제시하고 승인을 받는다. 공유판에서 중요한 표현 방식을 바꿀 때도 먼저 보고한다.

## 8. 내용 정확성 및 오개념 검토

수업 내용·회로·코드·실행 결과에 영향을 주는 변경은 구현 전에 관련 기초자료와 실제 동작 원리를 확인하고, 구현 후에는 설명·회로·코드·실행 결과가 서로 일치하는지 다시 검증한다. 내용 정확성 검증은 최종 단계에서 한 번만 수행하지 않고, 구현 전 근거 확인 → 구현 → 구현 후 상호 일치 검증의 과정으로 수행한다.

수업자료의 설명·개념·회로·코드·실행 결과·그림·애니메이션이 실제 피지컬 컴퓨팅 원리와 하드웨어 동작에 맞는지 기능 검증과 별도로 확인한다. 슬라이드, 교과서, 교육과정·성취기준, 공식 사양 또는 신뢰할 수 있는 기술자료, 실제 회로, 코드, 실행 결과, 시각 표현을 대조한다.

기술적 오류와 오개념 위험, 쉬운 설명의 왜곡 가능성, 중학교 1학년 수준 적합성, 용어 충돌, 앞뒤 슬라이드 간 모순을 살핀다. 오류 또는 오개념 가능성을 발견하면 임의로 내용을 바꾸지 말고 다음을 사용자에게 보고한다: 페이지·위치, 현재 설명/코드/회로, 문제, 원리와 근거, 학생의 오개념 가능성, 수정 필요 정도, 권장안. 표현 취향과 기술 오류를 구분하고, 해석 차이가 있으면 근거별로 제시한다.

## 9. 세 영역의 검증과 완료 기준

최종 완료 판단은 다음 세 검증을 모두 필요한 범위에서 통과해야 한다.

1. **내용 정확성·오개념:** 설명, 실제 원리·모듈, 회로, 코드, 결과, 시각 표현, 교육과정·성취기준과의 일치.
2. **기능:** 요청 기능, 정·역방향, 애니메이션 재실행, 회귀 여부, 전체화면, 16:9 및 화면 크기·비율 변화, UI 위치, 강조, 팝업, 실행 결과.
3. **코드·구조 최적화:** 중복 DOM/CSS/JS/이벤트, override, 미사용 코드·임시 패치, 재사용·공통화, 모듈화 필요성.

레이아웃, 위치, 크기, 애니메이션, 강조박스, 순서 번호, 회로선, 블록 이동, 팝업, 실행 결과는 코드만 보고 완료 처리하지 않는다. 최종 시각 검증은 GitHub Pages에 실제 배포된 결과를 기준으로 한다. localhost 또는 `file://`에서만 확인한 상태는 완료가 아니다. 실제 배포 화면을 확인하지 못하면 `구현됨 - 배포 화면 검증 필요`처럼 상태를 명확히 표시한다.

코드 작성, 한 방향 동작, 커밋·푸시, Pages 빌드 성공만으로 완료 처리하지 않는다. 미검증 항목은 추측하지 말고 `검증 필요`로 남긴다.

## 10. 안전 기준점과 상태 기록

- 커밋이나 푸시가 있다는 이유만으로 안전 기준점이라 하지 않는다. 해당 작업에 필요한 내용 정확성, 기능, 코드·구조 최적화 검증을 통과한 상태만 검증된 안전 기준점으로 기록한다.
- 큰 수정 전에 직전 검증 기준점을 확인한다. 문제가 생기면 패치를 더 쌓기보다 기준점과 현재 변경을 비교해 원인을 찾는다.
- 의미 있는 작업 단위마다 `WORK_STATUS.md`를 갱신한다. 상태, 수정 파일, 중복 제거·통합, 내용 정확성·오개념 및 사용자 검토, 기능·최적화·배포 검증, 남은 기술부채와 다음 작업을 기록하고 코드와 문서가 일치하도록 한다.
- 기록할 수 없는 항목은 사실처럼 채우지 말고 확인 불가 또는 검증 필요로 표시한다.
